# ПР-6. Шифрование игрового обмена

Рабочая ветка интеграции — `feature/vanya-encrypted-transport`. Unity 6000.3.10f1, NGO 2.7.0, Unity Transport, Bouncy Castle 2.7.0. Криптомодуль подготовила Арина, подключение к транспорту и локальные проверки — часть Вани.

## Где включается шифрование

Обычная кнопка создания игры и кнопка подключения идут в `RoofConnection.StartSession()`. Перед запуском NGO метод выбирает `EncryptedTransport`. Он оборачивает Unity Transport и шифрует сообщения NGO, включая ввод, снимки движения, инвентарь, счёт и синхронизацию сцены.

`CryptoUnityDriver` передаёт вызовы получения событий и отправки пакетов внутреннему UTP. Его транспортные заголовки, подтверждения доставки и параметры соединения остаются видны. Приложение скрывает игровое содержимое. Внутренний драйвер работает с собственными часами UTP, поскольку внутренний интерфейс метрик NGO закрыт. Для измерения фактических сетевых байтов используется UDP-посредник.

Для учебного сравнения запуск с `-roofPlaintext` выбирает обычный Unity Transport. Этот параметр нужен обоим процессам. Автоматического переключения с шифрования на открытый обмен нет.

## Обмен ключами

1. UTP устанавливает соединение.
2. Клиент создаёт новую пару X25519 и отправляет открытый ключ.
3. Сервер создаёт собственную пару, вычисляет общий секрет и отвечает открытым ключом.
4. Обе стороны применяют HKDF-SHA256. Salt содержит открытые ключи в порядке «клиент, сервер». Info различается для направлений `Rooftop/v1/client` и `Rooftop/v1/server`.
5. Клиент отправляет зашифрованное подтверждение, сервер проверяет его и отвечает своим зашифрованным подтверждением.
6. После проверки ключа внешний транспорт сообщает NGO событие Connect. Только затем начинается игровая синхронизация.

Сервер хранит отдельные ключи и счётчики для каждого транспортного ID. Неоконченный обмен ограничен десятью секундами. Одновременно допускаются до 16 транспортных сессий, игровые ограничения лобби проверяются отдельно. При отключении и shutdown собственные буферы ключей очищаются. При следующем соединении генерируется новая пара.

## Формат сообщения

Открытый ключ передаётся сообщением из 37 байт. Это magic `RF6`, версия 1, тип сообщения и 32 байта X25519.

Зашифрованное сообщение содержит 13 байт заголовка, 12 байт nonce, шифротекст и тег GCM 16 байт. Заголовок состоит из magic, версии, байта типа/канала и 64-битного номера в little endian. Низшие четыре бита байта типа обозначают Data=11, ClientProof=13 или ServerProof=14. Старшие четыре бита обозначают режим доставки UTP.

Заголовок входит в AAD. Его подмена приводит к отказу проверки тега. Для шифрования используется AES-256-GCM. Дополнительные данные увеличивают сообщение на 41 байт до добавления заголовков UTP/UDP/IP.

Транспорт использует перегрузку `CryptoManager.EncryptAES(key, plaintext, counter, aad)`. Nonce состоит из четырёх нулевых байт и 64-битного счётчика в little endian. Счётчик монотонный в пределах исходящего ключа, при исчерпании отправка прерывается. Для направлений применяются разные ключи. Повторная доставка UTP пересылает уже зашифрованное сообщение. Переподключение создаёт новые ключи. Исходный метод Арины с генерацией случайного nonce также доступен для отдельных вызовов криптомодуля.

## Подмена и повтор

До передачи сообщения NGO проверяется GCM-тег. Ошибка даёт запись `PR6 AUTH_FAIL peer=...`; содержимое сообщения игре не передаётся. Секретные ключи в лог не выводятся.

После успешной проверки тега обновляется окно принятых номеров. Окно в 64 сообщения допускает перестановку, отвергает дубликаты и слишком старые сообщения. Для режимов доставки используются отдельные окна, чтобы частые ненадёжные снимки не вытесняли задержанные надёжные сообщения. Отказ помечается `PR6 REPLAY_DROP`.

Обмен X25519 в этой учебной реализации требует внешней аутентификации открытого ключа для защиты от активного MITM. Успешное зашифрованное подтверждение показывает владение полученным ключом. Для подтверждения личности сервера нужен заранее доверенный ключ, сертификат или отдельный аутентифицированный канал. Шифрование и лимит сессий сами по себе не обеспечивают сетевую защиту от объёмной DDoS-атаки.

## Как воспроизвести

Собрать macOS Development Build через существующий `Rooftop.Editor.PracticeBuild.Build`. Локальные команды выполняются из папки проекта.

```sh
python3 Tools/check_security.py Builds/PR6/Rooftop.app/Contents/MacOS/game_cats Builds/check-security
```

Скрипт запускает по очереди открытый и зашифрованный обмен между отдельными процессами. Во втором прогоне после подключения клиента он меняет один байт зашифрованного сообщения, направленного серверу, и требует запись AUTH_FAIL. Затем проверяет завершение сценария движения и серверный отказ в раннем прыжке.

Файлы `plaintext.pcap` и `encrypted.pcap` можно открыть в Wireshark. Это записи полезной нагрузки, реально полученной локальным посредником, с восстановленными IPv4/UDP-заголовками. Порты источника/получателя взяты из адресов посредника; его исходящие сокеты и служебные поля IP в таком PCAP не воспроизводят захват сетевого интерфейса. Для отчёта с захватом интерфейса Катя отдельно записывает loopback или LAN через Wireshark.

В шифрованной записи можно найти hex `52 46 36 01`, открыть обмен ключами и последующие сообщения Data. Само наличие бинарных данных в UDP также встречается у открытого NGO, поэтому в отчёте нужно показать формат конверта, успешную игру и отрицательную проверку тега.

Меню Unity `Tools → Rooftop → Crypto → Run Self Test` проверяет RFC-векторы и криптомодуль, а также счётчик nonce, изменение AAD и окно повторов. Матч проверяется существующим `Tools/check_practice.py match`.

Этап Cloudflare выполняется по `docs/Cloudflare_Spectrum_Setup.md`. Настройки реального домена, origin и скриншоты добавляются после проверки подключения.

## Полученные локальные результаты

На macOS ARM64 в Unity 6000.3.10f1 прошли самотесты X25519, HKDF, GCM, счётчика nonce,
подмены AAD и окна повторов. Открытый и зашифрованный прогоны движения завершились.
Во втором прогоне сервер отклонил одно изменённое сообщение, после чего клиент завершил
прыжок через воздуховод. Старые проверки рыбок прошли с двумя клиентами в обоих режимах
репликации.

[Журнал](media/pr6/security-results.txt) · [Открытый обмен](media/pr6/plaintext.pcap) · [Шифрованный обмен](media/pr6/encrypted.pcap)

Полный матч с двумя отдельными клиентами завершился результатом 3:2:1. Реванш сбросил
состояние и закончился ничьей. Дополнительный прогон с задержкой 175 мс в одну сторону
и потерями 4% после подключения завершился перепрыгиванием воздуховода и серверным
отказом в раннем прыжке.
