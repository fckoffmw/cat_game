# ПР‑5. Оптимизация репликации (модуль предметов)

Исходный профиль и условия замера описаны в [Replication_Baseline.md](Replication_Baseline.md). Здесь — применённая оптимизация и сравнение «до/после» для модуля рыбок. Оптимизации движения котов и матча (Арина, Ваня) в этот документ добавляются по мере готовности (раздел 5).

## 1. Результат «до / после»

Условия идентичны: хост и два клиента, 60 рыбок, одна крыша, 60 секунд, шесть сдач, localhost без задержки и потерь.

| Показатель | До («полная рассылка») | После (рассылка по изменениям) |
|---|---|---|
| Реплицируемых рыбок | 60 | 60 |
| Исходящий трафик сервера за 60 с | 2 073 273 байт | 762 129 байт |
| **Исходящий трафик сервера** | **34,554 кБ/с** | **12,702 кБ/с** |
| Снижение | — | **63,24%** |
| Частота обновлений рыбок | 10 раз в секунду на каждую рыбку, всегда | Только при изменении: подбор, сдача, возрождение |

Формула: (34,554 − 12,702) / 34,554 × 100 = 63,24%. Ориентир методички — 40–60%; измеренный результат выше ориентира. Исходные данные: [media/fish-results.txt](media/fish-results.txt).

В оба числа входит весь исходящий трафик сервера, включая движение котов и служебный обмен Netcode, поэтому снижение именно по рыбкам оценивается по разнице «до / после», а не по абсолютным значениям.

## 2. Что применено

| Техника из методички | Реализация в Unity | Статус |
|---|---|---|
| Push-Based Replication (реплицировать только изменённое) | Состояние рыбки хранится в `NetworkVariable<ulong> holder` в [`RoofFish`](../Assets/Rooftop/Scripts/RoofFish.cs). Netcode передаёт его **только когда значение изменилось**. Периодическая полная рассылка (`FullStateRpc`, 10 Гц) в обычном режиме не используется | **Применено** |
| Net Dormancy (молчание неизменных объектов) | Достигается тем же механизмом: рыбка, которую никто не трогает, не отправляет ничего. Отдельного «спящего» режима объекта в Netcode нет | Эффект получен |
| Снижение `NetUpdateFrequency` для неважных объектов | Для котов: состояние шлётся каждый второй физический шаг (25 раз в секунду). Дальнейшее снижение частоты удалённых котов — задача Арины | Запланировано |
| Квантование (`FVector_NetQuantize`) | Позиции в `StateRpc` передаются полными `Vector3` | Не применялось |
| Replication Graph (релевантность по сетке) | Карта 24 × 16 помещается в поле зрения всех игроков, все объекты нужны всем. Отдельной фильтрации по зоне нет | Не применялось |

**Честная оговорка.** Методичка требует минимум две техники. Сейчас применена одна (рассылка по изменениям, она же даёт эффект Net Dormancy). Второй техникой планируется снижение частоты обновлений удалённых котов (Арина) или квантование позиции в `StateRpc`. Когда она будет готова, повторите замер и добавьте строку в таблицу.

## 3. Почему это сработало именно для нашей игры

- В игре «Коты на крыше» предметы (рыбки) — **редко меняющиеся объекты**. Состояние меняется только при подборе, сдаче и возрождении: в нашем сценарии это шесть сдач за минуту на 60 рыбок.
- Режим «полная рассылка» повторял каждую секунду 600 одинаковых сообщений (60 объектов по 10 раз) каждому клиенту, хотя нового в них почти ничего нет. Это избыточный трафик в чистом виде.
- Передача по изменениям убирает эту избыточность и не теряет точности: клиент видит подбор и возврат рыбки при первом же изменении. Игровая логика остаётся авторитетной на сервере (`RoofFish.OnTriggerStay` принимает контакт только на сервере).
- Для динамики другого рода (коты, которые двигаются постоянно) этот приём не помогает: их состояние меняется каждый кадр. Там эффект даст снижение частоты, квантование и сглаживание на клиенте.

## 4. Проверка корректности после оптимизации

В обоих режимах проверено (журнал [fish-results.txt](media/fish-results.txt)):

| Проверка | Результат |
|---|---|
| Рыбки доступны обоим клиентам | `CLIENT_READY fish=60` у обоих клиентов |
| Одновременное касание одной рыбы двумя котами | Рыбу получил один кот (`FISH_HELD single winner`) |
| Сдача, повторная сдача и возрождение | Сдача принята один раз, дубль отклонён, рыбка вернулась через 5 секунд (`FISH_FINISHED`) |
| Позднее подключение клиента | Клиент сразу видит 59 из 60 рыбок: одна в лапах у кота (`FISH_CLIENT visible=59`). После возрождения видит 60 (`restored=60`) |
| Шесть сдач за минуту | Выполнены в обоих режимах (`FISH_SAMPLE six deliveries`) |

## 5. Что нужно добавить по плану команды

- Арина: снижение частоты обновлений удалённых котов, проверка плавности и коррекции, частоты «до» и «после».
- Ваня: счёт при изменении, время окончания раунда при старте, итоговый замер на одинаковых условиях.
- Итоговая таблица «до/после» для всего проекта (рыбки, коты, матч) вместо только рыбок и повтор замера на двух разных компьютерах.
- Дополнительное задание методички (не выполнено): собственная функция релевантности `IsNetRelevantFor` и приоритеты `NetPriority`. В Netcode аналоги — видимость сетевых объектов для клиентов (`NetworkShow`/`NetworkHide`).
