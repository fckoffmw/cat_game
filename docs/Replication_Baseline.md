# ПР‑5. Исходный замер сетевого трафика (до оптимизации)

Документ описывает «до»-профиль для модуля предметов (рыбок). Замеры движения котов и матча выполняют Арина и Ваня по [плану команды](../task.md), их результаты нужно добавить в раздел 6.

## 1. Условия замера

| Параметр | Значение |
|---|---|
| Движок | Unity 6000.3.10f1, Netcode for GameObjects 2.7.0, Unity Transport |
| Версия кода | `main`, коммит слияния `e3880e9` (код модуля рыбок был в `feature/prediction`) |
| Сцена | Первая крыша 24 × 16, одна и та же в обоих замерах |
| Сетевые объекты | **60 рыбок**: 12 расположены в сцене и 48 создаёт хост при включённой галочке «60 рыбок» (6 секций по 8) |
| Участники | Хост и два клиента, отдельные процессы на одном Mac, всего три кота |
| Сценарий | После входа клиентов проверяются одновременный подбор рыбы, сдача и возрождение. Затем 60 секунд с шестью сдачами рыбы (одинаково в обоих замерах) |
| Длительность замера | 60 секунд |
| Сеть | localhost через посредник [`Tools/udp_lab.py`](../Tools/udp_lab.py) без задержки и потерь |

## 2. Что такое «исходный режим»

В Netcode for GameObjects состояние `NetworkVariable` уже передаётся только при изменении. Чтобы получить «базовый» сценарий с избыточной нагрузкой, как требует методичка, в проекте сделан **явно обозначенный учебный режим**: хост с галочкой «Хост: полная рассылка рыбок (10 Гц)» (`RoofConnection.FullUpdates`).

В этом режиме каждая рыбка ([`RoofFish`](../Assets/Rooftop/Scripts/RoofFish.cs)) **каждые 0,1 секунды** отправляет всем клиентам своё полное состояние (кто её держит), независимо от того, изменилось оно или нет. Это модель «реплицировать всё всем без ограничений».

## 3. Метод измерения

Посредник `udp_lab.py` стоит между хостом и каждым клиентом и считает размер UDP-пакетов, которые **сервер отправляет клиентам**. Счёт идёт с момента, когда закончилась стартовая проверка (подбор, сдача, возрождение), ровно 60 секунд, по обоим клиентам суммарно. Запуск:

```sh
python3 Tools/check_practice.py fish Builds/Rooftop.app/Contents/MacOS/game_cats Builds/check-fish
```

Скрипт сам запускает хост и два клиента, ведёт сценарий и записывает результат в `Builds/check-fish/full-traffic.txt`. Сохранённый итог — [media/fish-results.txt](media/fish-results.txt).

## 4. Результат: исходный профиль

| Показатель | Значение |
|---|---|
| Число реплицируемых рыбок | 60 |
| Исходящий трафик сервера за 60 с | **2 073 273 байт** |
| Исходящий трафик сервера | **34,554 кБ/с** |
| Частота обновлений рыбок | 10 раз в секунду на каждую рыбку, то есть 600 сообщений в секунду на клиента |
| Частота состояния котов | Ввод клиента — каждый физический шаг (при Fixed Timestep 0,02 с это 50 раз в секунду), состояние кота с сервера — каждый второй шаг (25 раз в секунду) |
| Событий изменения состояния рыбок за 60 с | 6 сдач (плюс подбор и возрождение при каждой) |

В число 34,554 кБ/с входит также сетевой обмен движения котов и служебный обмен Netcode, потому что посредник считает все пакеты сервера.

## 5. Какие объекты тяжёлые

**По устройству режима:** основная нагрузка исходного замера — 60 рыбок с обновлением 10 Гц. Они почти всё время не меняются (состояние меняется только при подборе, сдаче и возрождении), но передаются постоянно. Остальная часть трафика — коты (3 штуки) и служебные сообщения.

**Важно:** это вывод из устройства режима, а не измерение. Посредник считает суммарные байты и не раскладывает их по объектам. Для строгой раскладки по типам объектов нужно отдельно снять профиль (например, пакетом Multiplayer Tools с Network Profiler; в проекте он пока не подключён) и добавить таблицу в раздел 6.

## 7. Воспроизведение вручную

1. Соберите Development Build (macOS) или запустите два редактора.
2. На хосте включите «Хост: 60 рыбок» и «Хост: полная рассылка рыбок (10 Гц)» **до** нажатия «Создать игру».
3. Подключите двух клиентов, выполните одинаковый сценарий в течение 60 секунд.
4. Для измерения трафика поставьте посредник перед каждым клиентом (`--port 7778` и `--port 7779`, `--server 7777`), клиентов подключите к ним.
