# Коты на крыше — командный план ПР‑4 и ПР‑5

## Игра и старт проекта

Unity 6000.3.10f1, Netcode for GameObjects и Unity Transport. На первой 3D-крыше два кота собирают 12 рыбок. За один раз кот несёт одну рыбку. Сдача в свою коробку даёт одно очко и освобождает место для следующей рыбки. Через пять секунд после сдачи рыба снова появляется на исходном месте. Раунд длится 60 секунд. При равенстве максимальных результатов объявляется ничья.

В локальном проекте уже есть крыша 24 × 16, воздуховод с двумя обходами, коробки, сетевые рыбки, тестовая капсула и исходное серверное движение. ПР‑4 проверена на отдельном клиенте macOS, включая прыжок через вентиляцию и серверный отказ при раннем прыжке. Для блока Кати в ПР‑5 проверены спор за рыбу, позднее подключение, повторная сдача и возрождение. Измерено изменение трафика для 60 рыбок. Дальше команда подключает игровые коробки и матч, добавляет оптимизацию движения и проводит итоговый межплатформенный замер. Подробности приведены в [отчёте Кати](docs/Katya_Contribution.md).

Катя (Mac 2) запускает хост. Арина подключается с Windows, Ваня — с Mac 1.

Катя публикует общую базу на GitHub. Арина и Ваня клонируют её, открывают той же версией Unity и работают в отдельных ветках. Катя редактирует сцену крыши, Арина — визуальную часть персонажа, Ваня — префабы матча и интерфейса. Для работы втроём добавить третью коробку и точку появления до замеров ПР‑5.

Пока Катя делает ПР‑4, Арина может готовить модель и повороты визуального объекта кота в своём префабе. Ваня может делать коробки, матч и панели на тестовых событиях сдачи. Для сдачи ПР‑4 Катя может использовать капсулу.

## Интеграция игрового раунда

- Катя отвечает за рыбок, их модели, серверный подбор по контакту, запрет второй рыбки, возрождение и интерфейс CatInventory.TryDeliver().
- Арина соединяет визуального кота с готовым сетевым движением и выводит индикатор кулдауна.
- Ваня назначает игроку коробку. При входе в неё сервер проверяет владельца и активность раунда. Если TryDeliver() возвращает true, сервер добавляет одно очко. Ваня подключает лобби, таймер, боковой рейтинг, результаты, реванш и настройки.
- Вместе проверить две последовательные доставки, чужую коробку, одновременный подбор, окончание раунда и ничью. После реванша у всех игроков начальное состояние.

## Проверка матча и замеры Вани

Ветка `feature/vanya-match` подключает три зоны сдачи, лобби на 2–3 игроков, серверный раунд на 60 секунд, рейтинг, результат и реванш. Две зоны используют коробки текущей сцены. Оранжевая коробка и все три триггера находятся в префабе `Assets/Resources/RoofMatch.prefab`. Игрок получает цвет по стартовому месту. Позднее подключение в незаполненное лобби добавляет игрока с нулевым счётом.

Сервер сначала проверяет активность раунда и владельца коробки, затем вызывает `CatInventory.TryDeliver()`. Только успешная сдача обновляет строку рейтинга. Пакет начала раунда содержит серверное время окончания. Отсчёт у клиентов основан на синхронизированных часах NGO. Сервер фиксирует результат по истечении срока. При реванше он сбрасывает позиции, содержимое лап, рыбок и счёт.

### Воспроизведение на одном Mac

1. Использовать Unity 6000.3.10f1 и собрать `VentRoof.unity` как macOS Development Build. Для разбивки по типам объектов в сборке нужен Multiplayer Tools 2.2.12, который есть в ветке Арины.
2. Из корня репозитория выполнить команду. Параметр `--baseline-player` необязателен. Без него обе фазы используют один исполняемый файл, и режим репликации котов в обоих прогонах совпадает.

   ```sh
   python3 Tools/check_practice.py match Builds/Rooftop.app/Contents/MacOS/game_cats Builds/check-match \
     --baseline-player Builds/Baseline.app/Contents/MacOS/game_cats
   ```

3. Скрипт запускает три отдельных процесса, ждёт соединения и меряет один раунд на первой крыше с 60 рыбками. Маршрут включает по одному принятому сервером прыжку от каждого клиента и шесть сдач через игровые триггеры. Для повторяемости сценарий выставляет котов у рыбки и у коробки на сервере. Итог первого раунда 3:2:1. В режиме рассылки изменений автоматически проверяется также реванш и ничья 0:0:0.
4. В таблицу идёт сумма исходящей UDP-нагрузки хоста для двух клиентов. Делитель для кБ — 1000. Скрипт считает датаграммы отдельно от сообщений NGO. В журнале хоста строки `MATCH_METRIC` содержат число и объём отправленных RPC и обновлений `NetworkVariable`/`NetworkList` по типу объекта. UDP включает также пакетирование и служебный обмен.

### Прогон на устройствах команды

Для ручного замера «до» использовать базовую Development Build по составу из итоговой таблицы. При сборке задать `RoofMatch.BroadcastFullState = true` по умолчанию, затем на хосте включить полную рассылку рыбок. Режим «после» использует оптимизированную сборку с обычными настройками рассылки и с галочкой «60 рыбок».

Катя поднимает хост на Mac 2, Арина входит с Windows, Ваня — с Mac 1. В обоих режимах используются первая крыша, 60 рыбок, два клиента и один и тот же маршрут. Начать захват с нажатия «Начать раунд», закончить на появлении результата. За 60 секунд сделать два прыжка и шесть сдач по очереди 1, 2, 3, 1, 2, 1. Для объёма UDP на хосте суммировать нагрузку датаграмм с исходным портом 7777 к двум клиентам, вычитая 8 байт UDP-заголовка из длины каждой датаграммы. Сохранить настройки сети, хеши сборок, журналы профилирования и результаты обоих прогонов.

В рабочем режиме время окончания передаётся при старте, а строка рейтинга обновляется при изменении. Пакет с результатом уходит по окончании раунда.
